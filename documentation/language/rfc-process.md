# Valkyrie RFC 流程

## 概述

RFC（Request for Comments）是 Valkyrie 语言特性演进的标准化流程。任何对语言语法、语义、类型系统或标准库的重大变更，都必须通过 RFC 流程。

## RFC 生命周期

```
草案 (Draft) → 审查 (Review) → 接受/拒绝 (Accepted/Rejected) → 实现 (Implemented) → 稳定 (Stable)
```

### 1. 草案 (Draft)

- 任何贡献者都可以创建 RFC 草案
- 使用 `documentation/language/rfcs/` 目录下的模板
- 文件名格式：`rfc-NNNN-简短标题.md`（NNNN 为四位编号）

### 2. 审查 (Review)

- 审查期至少 7 天
- 需要至少 2 名核心团队成员审查
- 审查重点：
  - 动机是否充分
  - 设计是否与现有架构一致
  - 是否有更好的替代方案
  - 对现有代码的影响

### 3. 接受/拒绝 (Accepted/Rejected)

- 核心团队投票决定
- 接受条件：多数同意 + 无否决
- 拒绝时需说明理由，贡献者可修改后重新提交

### 4. 实现 (Implemented)

- RFC 接受后进入实现阶段
- 实现需包含测试用例
- 实现完成后更新 RFC 状态

### 5. 稳定 (Stable)

- 特性在至少一个正式版本中发布
- 无重大问题后标记为稳定
- 稳定特性不可再通过 RFC 移除（需走破坏性变更流程）

## RFC 模板

```markdown
# RFC-NNNN: 标题

## 状态
草案 / 审查 / 接受 / 拒绝 / 实现 / 稳定

## 摘要
一句话描述本 RFC 的目标。

## 动机
为什么需要这个变更？解决什么问题？

## 详细设计
具体的设计方案，包括语法、语义、类型检查规则。

## 替代方案
考虑过的其他方案及为何不选择。

## 影响分析
- 对现有代码的影响
- 对编译器的影响
- 对标准库的影响
- 对 LSP/工具链的影响

## 不兼容变更
是否引入破坏性变更？如果是，说明迁移路径。

## 未决问题
尚待讨论的问题。
```

## 不需要 RFC 的变更

以下变更不需要走 RFC 流程：

- Bug 修复
- 内部实现优化（不改变公共 API）
- 文档改进
- 测试用例补充
- 诊断消息改进
- 新增 Lint 规则（不改变语义）

## 编号分配

RFC 编号从 0001 开始递增。已使用的编号不可复用。
